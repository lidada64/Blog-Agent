## 方向判断

优先完善 Memory 与 RAG 合理，但不能把五类问题都归因于它们。建议以可验收的任务闭环推进，而不是先追求完整记忆框架。

| 问题 | 主要补齐项 | 最小验收 |
| --- | --- | --- |
| 长文本读取 | 批量正文读取、输入空间分配、覆盖记录 | 中部/尾部事实、无标题及大表格均能取证；不依赖80行反复翻页 |
| 多来源检索 | 混合召回、正文补查、去重及来源覆盖 | 标题无关键词但正文有定义的文章被发现并读取 |
| 用户约束 | 结构化任务契约、会话/任务/单轮作用域记忆 | 默认三条→本轮一条→下一轮恢复三条；compact及重启后仍正确 |
| 结果验证 | 确定性格式检查、正文语义支持评估 | 四条不通过三条要求；真实引用不能掩盖错误结论 |
| 用户要求分类 | 自然任务理解与证据类型路由 | 目录、正文、历史改写、运行能力和混合问题分流正确 |

Memory 管“要求是否被保留并送入本轮”，验证管“结果是否做到”；RAG 管“找到哪些证据”，分类管“当前任务需要哪些证据”。当前已有本地混合检索与任务状态，不宜从更换向量库或引入大型框架开始。

建议下一步先串通任务分类→有效约束加载→输出检查的小闭环，再补跨来源检索与批量读取，最后扩展按需记忆索引及整理。读取阻塞可作为独立小改动优先修复。复杂计划工具、联网扩展及 admin 写入功能可以后置；轻量任务状态和验收条件现在就需要。预算/恢复属于所有步骤的共同约束，不能用增加调用次数替代修复。产品总路线仍以 PRD 为准，本记录不重写路线表。

试用问题：Memory、按需检索和历史压缩分别解决什么？

来源：[Anthropic 原文](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)，2025-09-29。

执行：AI读取技能全文后，按其搜索→选择一手来源→定位相关章节→总结的方法试读。先限定官方域名检索，再打开一篇文章，并定位 Context retrieval and agentic search、Compaction、Structured note-taking；未展开其他搜索结果，也未启动子代理。工具名以当前可用的 web search/open/find 替代技能中的抽象名称。

摘要：按需检索通过轻量位置引用取回相关资料；结构化笔记将任务进展保存在上下文之外；压缩保留重要决定和未解事项，减少历史冗余。过度压缩会丢失后来才显得重要的信息。

置信度：原文概念归纳高；对本项目效果的推断中，未做 Blog-Agent 真实生成对照。覆盖范围仅为上述主题，不声称全文总结或多来源覆盖完成。

## 有用，但须限定用途

将它记录为“长文本按问题选读与摘要的候选策略”。保留分层阅读、正文去噪、来源标注与按来源整理；不直接照搬固定三个来源上限、长文件首尾选读、搜索摘要足以作答等规则。全面总结必须检查全部章节覆盖；跨来源综合不能因第一篇能答就停止。摘要保留原文定位，不能替代正文证据。

实测限制：open 即使要求 short 也返回较多正文，find 返回邻近大段内容；不能将只关注少量章节等同于工具只返回这些章节。未测输入/输出 token、时间或费用改善，也没有无技能基线，因此仅证明流程可用，不证明节省成本。技能列出的比例及 token 估值不作为项目指标。

接入候选：复用既定批量取证方案，工具返回 source/version/ranges、已覆盖与未覆盖区域；问答按相关性选读，全文总结按章节覆盖组织；回答预留与初读加一次集中补读保持总额度约束。全文超输入容量时明确限制；未来分层摘要必须保留证据定位并计入预算。验收采用长文中尾部事实、多文分散事实、冲突观点、代码/表格及低额度场景。当前仅完成试用记录，不标记 D9/D12 已修复，不形成性能类简历成果。
