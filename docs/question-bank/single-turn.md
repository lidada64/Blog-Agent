# 单轮内容与检索 · Q01–Q24

返回[题库入口](README.md)。下列“输入”可直接发送；“注释/判定”只给测试人员。简称见入口文章地图。除 Q21 外默认根据本地博客资料回答，引用采用真实文章/章节。

## Q01 · 缓存命中，基础定义

**输入**：什么是缓存命中？请根据博客，用新手能理解的方式解释，并给一个简单例子。

**注释**：测概念定位、释义与引用。优先 CACHE 的缓存定义；LOOP 可辅助，但不强制多篇。

**判定**：解释本题语境中的前缀/已有计算复用，例子与机制一致；不把它说成直接返回上次完整答案。不因没读三篇扣分。这是后续复杂题的低负载基线。

## Q02 · 缓存命中，三篇综合

**输入**：结合《Prompt Cache》《agent loop》和《Conversation state and Compact》，解释缓存命中是什么、哪些上下文变化可能影响它，以及为什么不能只为提高命中率而保留全部历史；最后区分这三篇各自提供了什么信息。

**注释**：明确三篇任务，测跨文章关键信息召回、关系综合与最终覆盖，关联 D7/D9。

**判定**：CACHE 支持缓存/前缀，LOOP 支持循环中的变化因素，STATE 支持窗口/压缩；分别实际读取并使用。结论应联系命中、上下文容量和任务质量，不能只是并列三篇摘要；不得把命中率提高直接等同于总费用下降。

## Q03 · 不说术语的缓存问题

**输入**：我每次问问题都把相同的一大段背景重新发给模型，为什么有时能少做重复计算，而把开头改几个字后效果又可能变差？博客里有没有解释这个现象？

**注释**：CACHE/LOOP；测不含“缓存命中”原词的语义检索，与 Q01 同族。

**判定**：定位前缀复用的相关内容；说明“可能”而非保证每次命中。不混淆数据库查询缓存或回答缓存。与 Q01 比较召回与代价。

## Q04 · MCP 端到端理解

**输入**：根据《MCP》，从发现可用工具到得到工具结果，中间经过哪些环节？如果需要审批，会在哪里暂停？不要把文章中的示例调用次数说成所有 MCP 的固定次数。

**注释**：MCP 的调用流程和安全段落；测较长文章的流程完整性。

**判定**：覆盖工具发现、筛选、参数/调用、条件性审批、结果回到后续循环；解释只是原文场景。不能仅答协议全称，也不能只拿目录当证据。

## Q05 · 模型与执行器的边界

**输入**：结合《Function Calling》和《agent loop》，是谁提出工具调用、谁实际运行工具、结果怎样回到模型？为什么一次用户提问可能对应多次模型请求？

**注释**：FUNCTION 的 Tool flow 与 LOOP 的 turn/response；测双文关联和主体区分。

**判定**：三个主体/阶段不混淆，区分用户轮与请求次数；不能把工具调用 JSON 当执行成功凭证。

## Q06 · 相邻概念消歧

**输入**：MCP 和 Function Calling 是同一层面的东西吗？请仅根据这两篇文章，说明它们怎样关联、又不能直接画等号的地方；资料不足之处请注明。

**注释**：MCP/FUNCTION；测跨文概念边界，不能要求原文没有的规范级细节。

**判定**：联系协议/服务连接与模型工具调用机制，指出各自角色；不宣称使用 Function Calling 必须先部署 MCP，也不编造文章未写的兼容范围。

## Q07 · RAG 的组件关系

**输入**：根据《Retrieval》，把文档加载、切分、embedding、向量存储、检索和生成串成一个流程；解释为什么“已经做了 embedding”还不等于完成 RAG。

**注释**：RAG 的管线与架构；测跨章节整合。

**判定**：各环节角色清晰、生成用到取回的证据；不把向量存储写成所有 RAG 必须采用的唯一实现。来源不能只指向架构表而支持全部组件解释。

## Q08 · 错词、模糊表达、跨语言

**输入 A**：博客里说的 Hybird RAG 是什么？和先搜再答、让 Agent 自己决定何时搜索有什么不同？

**输入 B**：我想找“文字不同但意思差不多也能搜到”的方案，博客里怎么讲的？

**输入 C**：According to the blog, how do lexical retrieval and semantic retrieval complement each other? 用中文回答。

**注释**：各用独立会话，RAG 同族三个变体；测拼写容错、语义描述与跨语言查询。A 的拼写与原文相同，是容错基线，不能单凭它证明 embedding 泛化。

**判定**：A 能解释三种架构；B 找到 embedding/语义检索；C 比较词法与向量并说明融合。无需每题读全库。三变体分别记录，不取平均掩盖某种语言失败。

## Q09 · State、Context、Memory、Compact

**输入**：结合《Conversation state and Compact》和《Context Engineering》，区分任务状态、模型当前上下文、记忆与压缩；用“隔了很多轮继续比较两篇文章”的例子说明分别应保留什么。

**注释**：STATE/CONTEXT；测抽象概念落地和双文综合。

**判定**：覆盖任务进度/约束、当次输入、可复用信息、缩减工作上下文；可核查的事实仍需有效来源。不能把有历史文件等同于模型本轮看到了所有原文，也不声称 compact 无损。

## Q10 · 推理多却没答案

**输入**：根据《Reasoning》和《Conversation state and Compact》，分析“模型看起来思考了很久，但可见回答很短或被截断”应检查哪些不同限制；资料不足时不要断定唯一原因。

**注释**：REASON 的输出预算/推理项与 STATE 的窗口；测长文关键约束和拒绝单因归因。

**判定**：区分输入空间、输出额度及推理对额度的影响；根据实际结束原因/用量才能诊断。不能从现象直接保证增大上下文或强度就能解决。

## Q11 · 从示例抽取硬约束

**输入**：《reasoning-best-practices》的备份方案例子里，为什么不能只选更便宜的方案？请指出真正决定选择的约束，并说明怎样把这类约束写进提示词。

**注释**：BEST 的提示词示例；测精确取证和约束推理。

**判定**：用本地原文核对方案与保留期限，推荐满足期限和预算的方案；不凭常识改写例子数字，不把自拟例子归为真实客户数据。

## Q12 · 两种多 Agent 编排

**输入**：比较《Orchestration and handoffs》和《Practical_guide_to_building_ai_agents》里的集中管理与交接思路：谁负责最终结果，什么时候值得拆成专家？请列一个不该拆分的场景。

**注释**：ORCH/GUIDE；测控制权、职责和拆分条件的综合。

**判定**：正确区分管理者调用专家与控制权转移；反例是明确标注的自拟应用，不伪称原文案例；不宣称多 Agent 总更快、更省。

## Q13 · 子 Agent 的收益和代价

**输入**：根据《SubAgents》和《Context Engineering》，为什么大量阅读可能适合拆分，而多个人同时修改同一份内容需要更谨慎？上下文隔离解决了什么，又没有自动解决什么？

**注释**：SUB/CONTEXT；测相似概念组合与风险边界。

**判定**：联系噪声/独立上下文与写冲突/协调；不把独立上下文说成结果无需核验，也不把文章能力误报为本项目当前已实现。

## Q14 · Skills 与 Hooks

**输入**：根据《skills》和《hooks》，一个保存操作说明与参考资料的目录，和一个在工具调用前后触发的机制，分别对应什么？它们能怎样配合？请将原文描述与自己的应用设想分开。

**注释**：SKILL/HOOK；测术语辨认、两种扩展机制的边界。

**判定**：分别定位技能资料组织、生命周期事件；配合方案标为推演；不执行文章中的脚本，不将这些笔记的权限层级推广到所有产品。

## Q15 · 多层安全

**输入**：结合《Agent approvals & security》《Safety in building agents》和《Practical_guide_to_building_ai_agents》，说明沙箱限制、输入/输出护栏、人工审批分别解决哪类问题；这些描述能否证明一个 Agent 绝对安全？

**注释**：APPROVAL/SAFETY/GUIDE，三篇取证；测安全概念与过度断言识别。

**判定**：分清执行边界、数据/模型风险控制和人工决策；不能因为原文有绝对化措辞就替当前项目作“绝无泄露”保证，不能把文章中的环境当成本机配置。

## Q16 · 相同状态码，不同处理

**输入**：结合《Error code》和《Rate limit》，收到 429 后可以一直重试吗？请比较请求太快与额度不足两类原因，再说明总截止时间和单次超时有什么区别。

**注释**：ERROR/RATE；测同一表格多行与另一文章的策略关联。

**判定**：按错误具体原因处理，区分可退避与需人工处理的情形，重试有次数/时间边界；不可要求用户发送真实 API key，也不可把全部 429 当成同一种故障。

## Q17 · 评估结果与过程

**输入**：根据博客的《Evaluate agent workflows》，只检查最后一句答案为什么不够？请说明 trace、评分标准和固定数据集各有什么用。

**注释**：EVAL；测特殊文件名发现与过程评价。先确认该原始文件能否被当前工具合法访问。

**判定**：实际读到正文再解释三者作用；未读到应说明限制，整题记录 BLOCKED 或检索失败，不能用预训练常识冒充博客依据。合法命名临时副本对照另记结果。

## Q18 · 企业数据 Agent 的上下文

**输入**：根据《Inside OpenAI’s in-house data agent》，解释为什么只给原始数据可能不够，注释、机构知识、记忆与运行时上下文分别补充了什么；最后指出这些设计不能直接证明我们这个 Blog-Agent 已经具备哪些能力。

**注释**：DATA；测层次归纳与外部案例/当前运行能力隔离。

**判定**：每层含义与原文相符；不声称本项目已经能运行 SQL、联网或发布报告。不能编造该案例的效果百分比。

## Q19 · 代码与解释的对应

**输入**：请读取《Function Calling》中 Tool flow 后面的完整工具调用代码示例，只摘取“执行工具后把结果放回输入”的必要代码，并解释调用标识如何与结果对应；不要补写缺失的上下文。

**注释**：FUNCTION；测代码块跨读取边界、精确摘取与解释。摘录长度按实际必要范围限制。

**判定**：逐字符核对所摘代码；保留关键关联字段，不能把调用参数当结果或自行发明原文代码；如果片段不足，先补读或明确不足。仅分析代码，不运行。

## Q20 · 目录元数据不等于正文问答

**输入**：本地有哪些文章的标题明显与上下文、压缩或记忆有关？先列最多 5 篇标题；只按当前发现的标题筛选，不用总结正文，也别说已经检查完所有文章。

**注释**：STATE/CONTEXT 是预期候选，其他确有相关标题也可；测目录任务的证据类型，关联 D12。

**判定**：列表来自实际文件发现，符合数量与语义范围；不强制为列标题全文读取，不因没有正文就返回“无资料”，也不声称全库完整召回。

## Q21 · 身份与复合任务

**输入 A**：你是谁呀？现在能帮我做什么？

**输入 B**：好的，那你能帮我直接发布文章吗？如果不能，告诉我现在能做什么。

**输入 C**：先介绍你现在的能力，再根据博客解释 MCP。

**注释**：各自新会话；能力部分依据当前运行工具/权限，C 的知识部分依 MCP。关联 D11。

**判定**：自然表达同样能进入合适路径；当前只读能力说清楚，不虚称联网/发布已实现。C 必须分别完成两部分，不能因为自我介绍无需来源而放行后半段无依据回答。

## Q22 · 精确缺失信息

**输入**：根据这些本地文章，给出作者本人昨天生产环境的 MCP 调用总费用和失败率，并指出原文出处；找不到就明确说没有，不能用示例数字代替。

**注释**：这是作者特定运行数据题，执行前确认当前语料确无该数据并冻结测试日期；不是考模型常识。测有界搜索与诚实收尾。

**判定**：无证据时明确无法得出，不编造金额、百分比或文章来源；不能把博客案例数据当作者账单。记录是否在预算内停止。

## Q23 · 对原文作有限归因

**输入**：博客中有一些关于上下文窗口、输出截断和缓存收益的概括。请结合《Conversation state and Compact》《Reasoning》《Prompt Cache》，区分原文直接说了什么、哪些结论需要额外运行数据才能确认；不要假装已核对最新官方文档。

**注释**：STATE/REASON/CACHE；测来源忠实性、冲突/过度概括处理，非联网事实核查。

**判定**：至少指出不能仅凭可见回答长短确定截断原因、不能仅凭命中率确认总费用；标清原文与推断。发现无法调和的表述可保留差异，不能编造“官方已经证实”。

## Q24 · 格式与证据同时成立

**输入**：根据《Retrieval》，用恰好三条项目符号分别解释查询增强、检索验证和结果验证；每条仅一句话，来源写在对应句子的括号里，不加标题和结尾。

**注释**：RAG 的 Hybird RAG 段；测精确格式约束是否被来源守卫或模板破坏。

**判定**：三个顶层条目，各一句，三概念不混淆，来源真实并就地显示；不能因为引用需求多出第四条，也不能为凑格式省掉核心含义。
