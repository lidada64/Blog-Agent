### D9 详细记录：一篇文章如何被读成多轮探索，以及用户为什么没有得到回答

尝试时间线见 [D9 尝试过程续篇](records-005.md#d9-尝试过程补记续篇)。本卷保留完整诊断，不因新增续篇删改历史证据。

记录日期：2026-10-12。状态：发生过程已核对，读取颗粒度问题已在临时文章上验证，解决方案仍待讨论和实施。这份记录只引用用户已经提出的问题和诊断元数据；不复制文章正文、完整会话、凭据或模型隐藏推理。真实知识来源在下文统一称为“文章 A”。

用户的要求是“我想知道什么是 prompt cahing，帮我解释下”。从用户角度，这是一次概念解释：希望得到定义、工作方式及适当例子。用户没有要求逐行审阅文章，也没有要求读完全部资料后才能作答。但 Agent 经过一串工具调用后，只给出停止探索的说明和几个已读取来源，随后进入等待下一条输入的状态。原问题没有得到解释，用户却需要猜测是否该换一种说法、重复提问或手动要求继续。这是任务没有完成时的恢复体验问题，不能通过把来源清单当成正常回复来解决。

日志显示，拼写并没有阻止这次检索。模型发出的 search_posts 查询是正确的“Prompt Caching”，limit=3，返回了三个候选。实际后续正文读取集中在同一篇文章 A、同一内容版本。最新预算为 v2，提示词也与当前版本一致；八个工具调用全部 completed。现有记录没有显示权限拒绝、工具失败、文件找不到或输入上下文超限，因此不应把这次失败归因于用户 prompt 写得不够规范。

读取过程可以完整还原。第一个模型步骤同时提出搜索和文章 A 的第 1–80 行读取。得到工具结果后，程序再次请求模型；模型接着读取第 81–160 行。随后它把每次读取量从 80 行改为 40 行，依次读取第 161–200、201–240、241–280、281–320 行，最后读取第 321–331 行。七个范围首尾连续、没有重叠，最后一段的 next_line 为 null。也就是说，这次并非不断重复读取相同正文，而是在同一篇文章上不断决定“再读下一段”，最后才读到文末。

用户所说的 readlines，在当前代码中对应 read_post(post_id, start_line, limit) 这个按行范围返回正文的接口。工具参数最多允许 80 行，正文返回另外还有 6,000 字符限制；返回值提供 next_line，提示后续还可以从哪里开始读取。底层 Python 的 splitlines 本身只是切分行，不会自主推理；真正增加模型往返的是：工具只返回一部分正文，程序把结果交回模型，模型决定继续读取，然后程序再次执行工具。这个循环由对话执行层逐次运行。模型可以选择相关范围或批量调用，并不被接口强制顺序读完，但本次实际选择了串行续读；其中每次 40 行也是模型自己的参数选择。

按日志中七段原文的字符长度相加，共返回 5,886 字符；按连续行范围补上段间换行，正文约 5,892 字符。这已经读完第 1–331 行，仍未超过当前 6,000 字符返回上限。前两次 80 行分别只返回 811 和 2,310 字符，后面五段分别为 534、332、562、1,262 和 75 字符，均没有撞到字符截断上限。空行多、短行多或 Markdown 排版稀疏时，行数不能准确代表文字规模。因此，对这篇具体文章来说，80 行上限与后续 40 行续读，把本可在字符上限内交付的全文拆成了七次工具读取。假设必须读全 331 行，即使每次都取满 80 行，也至少要五次读取。

这个机制已经用不含用户正文的临时样例验证：一篇 331 行、5,188 字符的 Markdown 小于 6,000 字符限制，用实际 SamplePosts.read 每次读取 80 行时，仍被切成 1–80、81–160、161–240、241–320、321–331 五段。这证明“字符容量够用，但行数上限导致多段读取”的接口现象。此前另一组模拟模型复现了“七次串行读取→第八次答案截断→只列来源”的端到端症状。两种复现支持的是运行机制，不证明同一个真实模型在任何问题上都会采取相同策略。

每次工具结果返回后，模型都会获得新的活跃上下文并生成下一步输出。服务记录显示，本轮八次模型请求的输入 token 依次为 2,620、4,627、6,709、7,605、8,366、7,964、8,363 和 7,711；合计输入用量为 53,965 token。这个合计是多次请求的输入量相加，包含重复发送的历史和证据，不是一次上下文长度，也不是 53,965 个独立知识 token。真实费用还需要价格、缓存命中及全部计费字段才能计算。新的一轮读取可能很短，但为了决定是否继续读，系统仍要再发送已经积累的上下文，这正是小工具结果带来较多模型往返的放大效应。

需要修正“每次都进行了大量 reasoning”的说法。八次请求都配置 high 推理强度，但服务报告的推理 token 依次为 258、14、33、15、96、14、14 和 1,728。中间大多数续读请求的推理用量不高；日志足以说明进行了反复模型请求、工具决策和上下文输入，却不能说明每次都深度推理。最大的推理用量出现在最后一次尝试回答时。全轮服务报告输出 3,055 token、推理 2,172 token；推理字段不应再与输出字段相加当成额外费用。上述都是服务用量观测，不包含或推断模型隐藏推理的内容。

为什么系统没有及时停下来回答？当前进展判定关注是否读到新的来源版本或行范围。七次读取都产生了新行，所以 no_progress 没有达到停止条件。它能识别重复查询、重复片段和空转，却没有判断“用户只是要解释一个概念，已经读到的资料是否足够”。工具返回了新内容，与用户任务需要新内容，是两件事。程序因此容许模型一直继续读取，直到接近模型请求上限，才强制关闭工具进入最终回答。

本轮总共允许八次模型请求，前七次都是获取资料和决定后续读取，只有第八次留给最终回答。第八次请求配置的 max_output_tokens 是 2,048，服务返回 status=incomplete，明确原因为 max_output_tokens，报告输出 2,048 token、推理 1,728 token。此时重生成逻辑要求总请求额度仍有剩余，但计数已经是 8/8，因此 output_retries 保持 0。现有恢复逻辑并非没有实现，而是在最需要它的最后一次回答失败时，没有预留可用额度。模型请求耗时合计约 26.64 秒，本次触发的是请求次数和输出上限，不是记录中的 120 秒耗时限额。

程序随后没有执行不完整响应中的工具调用，而是产生 output_truncated 的降级回复，列出已读取来源及行范围。业务结果虽然标为失败类别，技术轮次仍被结束，系统状态变成 waiting_user。用户看见的是“停止探索”，然后又到了输入提示符。这个表达掩盖了两个不同阶段：探索结束本来应当意味着开始回答，而本次实际是回答生成失败。来源清单可以帮助恢复和排查，但不能替代解释，更不应让用户承担重新组织问题或从头触发检索的工作。

因此，当前证据支持一条完整因果链：按行返回的小片段与模型串行续读增加往返；持续获得新行让无进展检测无法收敛；过多探索用完了只预留一次回答的总请求预算；最后回答又遇到输出截断；没有剩余恢复额度，只能回到用户输入。读取颗粒度是本次的重要诱因，最终回答的输出/推理配置和恢复预算是另外两个环节。改变读取工具有望减少前段往返，但尚不能保证最终生成永不截断；反过来，只增加输出或请求额度，也没有消除串行续读的结构性开销。

用户提出的第一个方向，是让 read 工具一次调用能够读取整篇文章。对于本例，全文约 5,892 字符，若满足实际模型输入及证据预算，一次返回全文可以消除“继续读取下一批行”的多次决策。值得讨论的是按文章大小选择全文或段落读取，是否支持一次获取多篇有界文章，以及清楚说明全文是否完整。不能简单去掉所有大小限制：超长文章仍可能造成过宽输入，长文概念解释也可能只需要少数段落。来源、内容版本、引用行号、权限和目录边界都需要保留。这个方向直接改善取资料的接口颗粒度，尚未实现，也没有测量真实模型的成本/质量变化。

第二个方向，是通过语义 RAG 找出用户需要的段落，用较少证据完成回答。目标是将“模型逐段翻全文找信息”改为“检索器先选择相关证据，再交给模型解释”。Markdown 分块、关键词/语义排序、必要上下文补齐和一次组装多个片段，需要作为一个整体讨论；如果语义工具仍只给文章 ID，之后继续要求模型逐行读全文，就可能保留同样的调用链。对于技术术语和精确标识，也应保留关键词基线或讨论混合检索，不把向量检索预设为唯一正确路径。检索与分块可能丢失背景，需保留标题、来源和相邻上下文；这些取舍在 [Anthropic 的检索工程说明](https://www.anthropic.com/engineering/contextual-retrieval) 中也有讨论，但其测量结果不能移作本项目成绩。

“最低成本”目前是目标，尚不能作为语义 RAG 的既定结果。需要同时计算索引构建/更新、embedding、可选重排、回答、补查及恢复的开销，并测量引用支持和回答完成情况。对于本例这样不长的单篇文章，全文一次读可能更简单；对于跨文章、同义表达或长文定位，段落检索可能更有价值。这两个方向可以组合：检索决定读什么，读取工具决定一次交付多少，两者共同减少不必要的模型决策。下一次讨论应在同一授权样例集上比较现有按行读取、一次全文读取、关键词段落检索和语义/混合检索，而不是先承诺某个方向一定最省钱。

无论选择哪条路径，用户体验的验收都必须保留：获得足够资料后给出解释；最后回答失败时在已保存任务上自动进行有界恢复；恢复仍失败时明确标记原问题未回答并支持继续原任务，不要求用户重复输入，也不把来源清单当成任务完成。总请求、耗时、输入规模和权限仍应受约束，但约束如何分配以及失败如何恢复，应由系统承担。
