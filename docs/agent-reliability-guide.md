# Blog-Agent 可靠性改进简要指引

2026-10-17。供用户理解方案、Codex认领任务时阅读。产品范围以 [PRD](PRD.md) 为准，进度见 [TASKS](TASKS.md)。默认输出已提高到 **8192 tokens/请求**；长文导航/分段进展、存储错误分类及协议拦截已进入首批实现，其余设计仍待实施。更易读的现状与顺序见[组件清单](agent-components.md)。旧轮恢复沿用已保存额度，新用户轮使用新默认；已运行进程需重启。

## 1. 任务理解：先确定“需要什么证据”（D11 / D12）

**建议：固定规则处理明确指令，语义判断处理自然表达，程序控制权限与验收。** 不再把未命中正则的问题一律归为文章正文。

形成结构化任务契约：任务类型、证据类型、目标文章、明确约束、待澄清项。区分目录元数据、运行能力、文章正文、历史与改写；混合问题拆成子目标。自然问法允许模型提出契约，程序校验字段；分类尽量并入首次规划请求，若独立调用则计入预算。无法确定且影响执行时澄清。能力来自真实工具配置；模型分类不能授予权限，目录标题也不能支撑正文结论。

代码入口：`answer_contracts.classify`、`RetrievalPolicy.catalog_question`。验收：同义、长句、混合问法走对流程；“只列标题”不被正文引用规则拒绝。

## 2. 会话记忆：方向可行，补上作用范围（D7 / D12）

**采用你的“存储→加载→提取→整理”管线。** `MEMORY.md`维护简短索引，正文按需读取；每次存储同步索引。四类是内容分类：user（用户偏好）、feedback（做事要求）、project（任务背景）、reference（资料位置）。它们不能代替作用范围。

每条另记：来源轮次、作用范围（会话/任务/单轮）、有效状态、替代关系。用户明确说“本轮两条”只覆盖本轮，之后恢复“默认三条”；明确要求优先于模型推断，冲突不明时澄清。首版只在同一会话内有效，不自动变成跨会话用户画像。

加载顺序：整理/压缩历史 → 必需约束直接加载 → 有界索引及相关记忆加载 → 统一检查输入预算 → 生成。有效硬约束每轮必带，不依赖side-query是否召回。当前用户要求先进入本轮契约，不能等轮末提取才生效。

你的双路径可保留：每轮冻结一次索引；轻量side-query结合当前问题、最近对话和索引返回文件ID，程序校验归属后读取，失败退回关键词。相关记忆放在明确标注的会话数据块；即使索引位于system，也不把用户文本、文章内容提升为系统规则。轮内工具和证据输入仍正常更新。

轮末只从用户表达提取候选记忆，区分偏好与单轮要求；“没有tool use”是轮末信号，任务成功还须通过终态检查。失败轮中明确的用户约束仍可保留，失败答案不能当成事实。写入用轮次ID去重、原子更新和可恢复记录。文件达到10个可触发低频整理，同时考虑体积与冲突；合并保留来源、范围和撤销信息。

记忆放在忽略的运行目录，按会话/模式/目录隔离；提取、side-query、整理都计入持久调用/费用预算，维护失败不抹掉已交付答案。代码入口：`TaskContextBuilder`和会话持久化。验收：切题、compact、重启后默认要求仍有效；临时覆盖自动结束；检索失败不丢硬约束。

## 3. 读取与停止：长文导航可行，先允许恢复（D9 / D12）

2026-10-18更新：长文总结的目标交互改为“预先维护的整体摘要＋章节目录→用户选章深入”，详见[分层摘要方案](hierarchical-article-memory.md)。下述导航与批量原文读取继续作为细节取证基础；新摘要存储、后台维护及派生证据契约尚未实现。

**采用你的结构导航思路，但摘要线索只帮助选位置。** 长文返回有界目录：标题层级、稳定章节ID、行范围，可附短的加粗片段、表头或代码块语言；跳过代码中的伪标题，巨大表格不全文塞入目录。模型选择章节后，由定位读取工具返回真实正文，仍做版本和可见范围核验。无标题时退回段落范围/关键词定位；导航不足允许预算内补读。

先修改停止逻辑：明确区分发现、定位、读取、回答；全文过长返回`needs_segment_read`，属于可恢复转换，不能与空搜索累计成“失败两次”。有效定位/新增正文算阶段进展，重复相同范围且无新增才计无进展。保留请求、时间、工具硬上限和回答预留，防止无限导航。

代码入口：`RetrievalPolicy.execute/identities/stop_reason`、`SamplePosts.read_full`及既有章节解析。验收：空搜索后遇到长文仍能分段；无标题长文可读；重复导航最终有界停止，恢复不重置预算。

## 4. 答案验收：Memory必要，但不够（D12）

**Memory解决“要求有没有送到”，验收解决“答案有没有做到”。** 从当前问题和有效记忆生成可检查的输出契约；程序检查最多/恰好几条、必需比较对象、指定结构等明确要求，避免把普通文章回答直接判通过。失败时在预算内反馈具体差异并修复一次，仍失败则明确未满足。

语义支持另验：保留来源存在/版本/可见范围检查，再检查关键结论能否由所引正文支持；引用存在不等于结论成立。先建立逐断言人工校准样本，再评估有界模型审查是否值得接入；未实现或不能判定时保留“语义未验证”，不宣称可靠通过。

代码入口：`requested_shape`、`audit_sections`、`record_reply`。验收：三条限制不能放过四条；真实来源配错误结论不能被当成语义通过。

## 5. 错误解释：区分可处理事项与程序故障（D20 / D13）

**你的两类用户表达可以保留，但内部不能仅按“谁的错”分类。** 请求不清、缺资料、权限不允许、预算停止、服务异常、持久化失败、模型协议异常分别编码，携带发生阶段、原始原因、是否可重试和恢复状态。

- 用户可处理：说明缺什么及下一步，例如“请指定要比较的两篇文章”；权限限制如实说明。模型生成了错误工具参数，不归咎用户。
- 程序或服务异常：说明失败步骤、已完成部分、保存状态及可用恢复方式，例如“保存会话失败，当前轮尚未确认写入磁盘”。未知原因明确未知。

实现上用独立的策略拒绝、参数、持久化异常类型；只由真正权限检查产生越权事件。`PermissionError`来自文件保存时归入存储错误。保留最早阻断原因和后续症状；先识别协议异常，再检查引用，不让引用错误覆盖读取中断。伪工具文本不能执行或直接交付。

代码入口：`atomic_write_json`、`runner.finish_pending`、`denied_calls/record_reply`。验收：注入保存失败仍报存储错误；读取中断保留原始原因；真正越权仍拒绝。

## Codex执行顺序

先做错误分类与阶段恢复，再做任务契约、会话记忆、答案验收；长文导航在阶段恢复后接入。每次认领一个可验证的小改动，先保留失败用例，再实现并验证。共享循环改动放`code/agent_core/`，博客逻辑放`code/blog_assistant/`；复用现有任务记忆、章节树和预算。新增付费调用方案先核算总额，真实调用另获额度授权。更新既有难题ID，区分设计、离线通过和真实质量通过。
