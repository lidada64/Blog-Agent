# 开发难点分级与简历素材记录

## 触发与目标

开发中 AI 判断遇到 bug、难点或反复失败时立即使用；用户指出“大难题”时使用；已有难题形成方案、修复、验证或复发时更新同一条记录。普通知识问答、临时笔误和无异常的例行操作无需生成难题条目。

记录与分级是辅助任务，不替代用户当前开发目标，不授权付费模型调用、发送消息、提交或发布。

## 找到唯一台账

读取当前项目 AGENTS.md 和 TASKS；沿已有指针找到简历素材/问题台账，保持一个业务问题一个 ID。Carrykit 与 Blog-Agent 共用 `D:/CST/code/Agent/docs/project-highlights/README.md`，不在博客另建副本。其他项目使用其配置的台账；没有配置时先寻找现有简历素材文档，无法确定再询问位置。

读取匹配的问题和排序索引。同一失败链条的新诊断补进原条；修复后出现不同根因或新回归，可新增条目并链接旧 ID。先核实是否已经记录，不因换聊天重新编号。

## 分卷存储与容量

台账是独立文件夹，以 README.md 为唯一入口；Carrykit/Blog-Agent 使用 `D:/CST/code/Agent/docs/project-highlights/`。入口只保留当前优先事项、分级排序和分卷/ID 定位，正文写入 records-001.md、records-002.md 等连续编号文档。现有旧单文件仅为兼容跳转，不继续写入。

每卷默认上限 6,000 个非空白字符（包含 Markdown 标记，是保守容量统计，不是 token 数）。写入前对正文草稿运行 [scripts/plan_volume.py](scripts/plan_volume.py)：输入 --ledger-dir 和 --incoming-file，默认 --limit 6000；脚本仅读文件并建议目标卷，不自动写台账。

新增记录优先追加末卷；预计超限就按 [references/volume-template.md](references/volume-template.md) 新建下一卷。更新已有 ID 先查所在卷；若更新会超限，在最新可容纳卷写同 ID 的“续篇”，原卷保留链接并由入口明确当前状态与完整位置。详细历史不整段复制到续篇，ID 不重新编号。单段超限时按尝试阶段或方案/验证边界拆为续篇，表格、代码块及一条证据不得从中切断。

写完复查各卷长度、相邻卷链接、同 ID 续篇链和入口索引。入口接近上限时先把非索引的详情移到分卷；若索引本身已过大，按等级分页为 index-001.md 等，README 只保留入口与当前优先事项。不能把一篇长文改成一个不断增长的巨大 README。旧链接需要更新或保留简短跳转；移动文件同步修正相对证据链接。

## 四维分级

每维记录分值及依据；这是工程初评，不是性能指标。修改范围未实现时标“预计”，以实际改动复核。频次只依据可见用户追问或已有记录，助手重复说明和工具调用不计入；历史不足标未知，不冒充零次。推测难度注明置信度，待根因/修复结果更新。

| 维度 | 0 | 1 | 2 | 3 |
| --- | --- | --- | --- | --- |
| M 修改规模 | 文档/配置或局部参数 | 单模块逻辑 | 多模块或接口/状态协同 | 多子系统、数据迁移或架构重构 |
| F 用户提问频率 | 可见范围无追问 | 一次澄清/追问 | 多次围绕同题追问 | 反复失败、重新提出同题并持续追问 |
| D 推测难度 | 原因明确、已有直接修法 | 局部定位与修复 | 多因素交互、故障复现/边界取舍 | 架构取舍、实验校准或跨阶段恢复 |
| U 用户明确判定 | 用户未明确称为大难题 | — | — | 用户直接明确指出该问题是“大难题” |

U 只能是 0 或 3，不能从“用户问得多”推断 U=3。保留直接表述的依据，普通失败抱怨不自动算明确“大难题”。

总分 M+F+D+U：0–3=L1 小，4–6=L2 中，7–9=L3 难，10–12=L4 大。U=3 时至少列 L4，显示实际总分与用户判定，不虚增其余分数。未知维度用 null，显示分数/等级范围，单独放待评区。

用 [scripts/rank_challenges.py](scripts/rank_challenges.py) 生成分级表，防止排序和计算不一致。输入 JSON 数组，每项含 id/title/status、M/F/D（0–3 或 null）、U（0/3 或 null）、basis（四维依据字符串）。标准输入输出：

```powershell
Get-Content <临时评分输入.json> -Raw | python <skill目录>/scripts/rank_challenges.py
```

完整评分按等级、总分、ID 从小到大排列；待评项排在单独区域，位置不表示它们更难。分级表是台账的索引，详细现象、方案和证据仍按 ID 保存。难度排序不替代修复优先级：安全问题或当前阻塞可以优先处理。

## 写入与持续更新

每次触发后完成以下记录，再继续当前任务或结束回复：

1. 记录现象、用户影响、复现条件、证据定位、根因的确定性，以及 M/F/D/U 与依据；状态选诊断中/已复现待修/方案已定待实施/已修复待验/已验证/复发。
2. 按时间记录实际尝试：执行者（用户/AI/共同）、当时假设、具体操作与改动、观察/证据、成功/失败/不确定、下一步及保留/放弃理由。用户要求“我是如何尝试”时区分用户亲自执行与 AI 协助，未知执行者不推断。失败尝试也保留；历史材料不足就标未记录，不编造还原，不记录模型隐藏思维或逐字内部推理。
3. 方案形成时补实现位置、取舍、预期效果和验收方法。方案不算完成成果；输出 token、推理 token、输入 token、请求次数和耗时分别写，不把不同预算混为一谈。
4. 修复后补实际改动、检查结果、失败/环境限制和剩余风险；只有有证据的改善才写入简历亮点。没有对照就描述能力变化，不编造百分比或准确率。
5. 重算该问题分级，更新从小到大的索引。历史难度不会因问题已解决自动降为零；保留状态和修订日期。
6. 仍阻塞下一步时在 TASKS 和台账续接处链接该 ID；修复后解除旧提醒。最终简要告知记录位置和变化，避免把写文档当成修复已完成。

原始文章、完整对话、凭据和隐藏推理不复制进可提交台账；保存脱敏元数据、证据路径/hash 和观测用量。用户自己明确请求记录的发生过程可以用自然语言归纳。遵循目标仓库的验证要求。
